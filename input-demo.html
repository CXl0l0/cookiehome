THE INPUT LAYER · A PROFESSOR-READY WALKTHROUGH

Understand the signals before interpreting the person.

Cookie Homes uses two core signals plus a linking catalog: what the browser observed, what the site’s consent platform says the user chose, and evidence connecting a cookie to its vendor and purpose. The catalog is necessary for attribution; neither signal replaces asking the user what they want.

✳
Inputs matter just as much as the output.
Good preference extraction starts with good context. Unknown evidence stays unknown; it never silently becomes consent.
INPUT 01◉

Observed cookie metadata

What did the browser receive? Technical details from Set-Cookie: cookie name, setting domain, path, lifetime, and security flags.

Example observationbasket_id · shop.test · Secure · HttpOnly

↳ Describes a cookie’s handling—not its purpose or whether the user agreed to it.

INPUT 02☷

CMP consent signal

What choice did a consent platform record? When available, a GPP or TCF signal can describe choices for supported purposes or vendors.

Example decoded signalNorthstar Ads · personalised ads · deny

↳ Describes a choice—it does not list every cookie that implements that purpose.

LINKING INPUT⛓

Site purpose catalog

Which vendor and purpose does a cookie belong to? A site disclosure or verified inventory connects cookie name/domain to vendor ID, purpose ID, category, and a plain-language explanation.

Example mappinglayout_choice → fresh-shop / saved-layout

↳ This third input is the attribution bridge. Without a match, show an unknown guest and keep CMP choices unlinked.

PROTOTYPE INPUT CONTRACT

Records in, guests out

These are two separate inputs. Cookie purpose mappings are a versioned site disclosure/catalog, not guessed from cookie flags or names.

ADAPTER OUTPUT

Guest roster for this home

CMP records received

The adapter preserves each observed record. A catalog match assigns one of the five categories and links the cookie to vendor/purpose IDs. Essential starts inside; a matching readable CMP decision is reflected; all other known guests wait at the door. Unknown purpose stays unclassified at the door. CMP choices without a cookie/catalog match are still displayed but are not applied to a guest.

GRACEFUL WHEN THE WEB CHANGES
New cookie? New purpose? Keep the pipeline; extend the catalog.
Store new raw observations and versions without rejecting the record. Add a mapping only when evidence is available. Until then, show an unknown guest, ask for clarification, and apply no preference. Future work: move purpose definitions into a versioned data registry so new categories can use the same validated decision flow. This prototype demonstrates the flow with fixtures; it does not yet implement live browser or CMP adapters.
